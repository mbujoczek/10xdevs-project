<decisions>

1.  User preferences (e.g., language) will be stored in the browser's `localStorage`, not in the database.
2.  A new `FlashcardGenerationEvents` table will be created to log AI generator usage metrics. It will contain `UserId`, date, the number of proposed candidates, and the final number of accepted/edited flashcards.
3.  User accounts will not be deleted. Flashcards deleted by the user will be marked as deleted (soft delete) by changing the status in the `Status` column to 'Deleted'.
4.  The original text from which flashcards are generated will not be stored in the database.
5.  No rate-limiting mechanism for flashcard generation will be implemented at the database level.
6.  For manually created flashcards, the `Source` column will default to 'Manual', and `Status` to 'Not applicable', which will be implemented as a `DEFAULT` in the database schema.
7.  An `SRSLastGrade` column (type `int`) will be added to the `Flashcards` table to store the last grade of a flashcard.
8.  All database objects (tables, columns) will be named in English.
9.  Audit columns `CreatedAtUtc` and `UpdatedAtUtc` will be added to the `Users`, `Flashcards`, and `FlashcardGenerationEvents` tables.
10. Primary keys in the tables will be of type `INT`.
11. The `Question` column will have a maximum length of 200 characters, and `Answer` 500 characters.
12. Errors will be logged to a dedicated database table using the Serilog library.

</decisions>

<database_planning_summary>

Based on the discussions, the SQL Server database schema for the "AI Flashcard Generator" MVP will consist of four main tables: `Users`, `Flashcards`, `FlashcardGenerationEvents`, and `Logs`.

Main schema requirements:

The schema is intended to support the application's core functionalities: user authentication, flashcard management, an SRS repetition mechanism, and collecting metrics on AI usage. All object names will be in English. The `Question` and `Answer` columns will have limited lengths (NVARCHAR(200) and NVARCHAR(500), respectively). Primary keys will be of type INT.

Key entities and their relationships:

1.  **Users**: Stores authentication data. Contains `Id` (PK), a unique and case-sensitive `Username`, and `PasswordHash`.
2.  **Flashcards**: The main table storing all flashcards. It has a many-to-one relationship with the `Users` table via the `UserId` foreign key. It includes columns for content (`Question`, `Answer`), origin (`Source`), status (`Status`, including 'Deleted' for soft delete), and a complete set of fields for the SRS algorithm prefixed with `SRS` (`SRSInterval`, `SRSRepetitions`, `SRSEaseFactor`, `SRSNextRepetitionDate`, `SRSLastGrade`).
3.  **FlashcardGenerationEvents**: A table for logging metrics. It has a many-to-one relationship with `Users` (`UserId`). It stores information about each flashcard generation event, including the number of candidates and the final number of accepted cards.
4.  **Logs**: A technical table, created and managed by Serilog, for storing error logs from the backend application. Its structure will conform to the standard Serilog SQL Server Sink schema.

Security and scalability:

- **Security**: User passwords will be hashed. Data isolation between users will be ensured at the application level by filtering all queries by the logged-in user's `UserId`.
- **Scalability and performance**: Indexes will be created on foreign keys (`UserId`) and on columns frequently used in `WHERE` clauses (e.g., `SRSNextRepetitionDate`) to ensure high query performance. Using the INT type for primary keys is sufficient for the scale of the MVP.

</database_planning_summary>
